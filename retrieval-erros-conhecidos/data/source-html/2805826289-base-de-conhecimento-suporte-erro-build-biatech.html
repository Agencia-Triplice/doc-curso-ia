1.1 Erro 500 na esteira ao publicar a imagem Docker no Nexus - ERROR: failed to build: received unexpected HTTP status: 500 Server Error

🧠 Resposta da BIA TECH – Erro de conexão entre o GitHub Actions e o repositório Nexus

Olá! 👋

Identificamos que a falha ocorreu durante a etapa de Build/Push Docker Image devido a um erro de conexão entre o GitHub Actions e o repositório Nexus. Esse é um erro que pode indicar uma falha no Registry do Nexus o que inviabiliza a publicação de novas imagens geradas.

🔍 O que isso significa?
O processo não conseguiu publicar a imagem Docker, resultando em um erro HTTP 500.

🛠️ Etapa de falha
Build/Push Docker Image

✅ O que você deve fazer:

  • É necessário acionar o time de Ferramentas para verificar a integração e restaurar a conectividade.
  • Você pode tentar executar o re-run jobs failed do GitHub para verificar se a conectividade com o Registry foi estabelecida.

🎯 Motivo:
Erro Build

👥 Time responsável:
Ferramentas

1.2 Erro 400 na esteira ao publicar a imagem no Nexus na etapa de build

🧠 Resposta da BIA TECH – A versão do artefato publicado no Nexus já foi publicada

Olá! 👋

Identificamos que o erro 400 ocorreu devido ao fato de que a versão do artefato publicado no Nexus já existe. O processo de CI realiza uma requisição para o Nexus na tentativa de publicar o artefato gerado pela esteira na etapa de build e então nesse caso falha porque a própria ferramenta não permitir publicar versões de artefatos que já foram publicadas em builds anteriores, lançando a seguinte mensagem: 400 Repository does not allow updating assets

🔍 O que isso significa?
A esteira checa se a versão adicionada no pom.xml ou package.json já existe no Nexus e caso exista o erro 400 é gerado.

🛠️ Etapa de falha
Execute fortify / Publicar aplicação NodeJS/Angular / Upload config and swagger to nexus / Upload Package to Nexus

✅ O que você deve fazer:

  • Acessar o diretório principal do projeto.
  • Verificar o arquivo de configuração de build. Dependendo da tecnologia pode ser pom.xml, package.json, ou main.py.
  • Localizar a tag de version e incrementar a versão da aplicação.
  • Efetuar um novo build.

Por exemplo, no caso do pom.xml:

<groupId>br.com.bradesco.cardtech.cloud</groupId>
<artifactId>svmp-srv-visa-notifica-consumidor</artifactId>
<version>0.0.2</version>

Deve ser incrementada para 0.0.3.

🎯 Motivo:
Erro Build

👥 Time responsável:
Desenvolvimento

Olá! 👋

Identificamos que a etapa SonarQube Quality Gate Check falhou devido à configuração incorreta do plug-in JaCoCo ou ausência de cobertura adequada de testes unitários.

🔍 O que isso significa?
Como consequência, o SonarQube não está interpretando corretamente o arquivo jacoco.xml, comprometendo a análise de cobertura.

🛠️ Etapa de falha

✅ O que você deve fazer:

  1. Verificar se os testes estão corretamente na pasta src/java/test.
  2. Executar localmente:
    • mvn clean install jacoco:report
    • mvn jacoco:report
  3. Validar o relatório na pasta target.
  4. Se cobertura < 90%, aumentar testes.
  5. Ajustar plugins Jacoco e maven-surefire no pom.xml.

1.8 Erro na etapa de Recuperando informações do projeto - Falha de autenticação (401 Unauthorized)

🧠 Resposta da BIA TECH – Falha ao recuperar informações do projeto devido a permissão

Olá! 👋

Identificamos que a etapa de Recuperando informações do projeto falhou devido a uma falha de permissão na tentativa de baixar dependências de um repositório Nexus não autorizado.

🔍 O que isso significa?
Significa que o build irá falhar, pois não há permissão para baixar as dependências de um repositório do Nexus que seja divergente do configurado para a aplicação.

Você pode consultar qual a VS_KEY está configurada no repositório do GitHub.
Por exemplo: se a VS_KEY configurada for BRAIN, então o único repositório que deve ser acessado para carregar as dependências do projeto seria o brain-maven-central.

O que pode estar ocorrendo é que há alguma configuração de repositório adicional no pom.xml causando essa falha.

✅ O que você deve fazer:

  • Acessar o projeto da aplicação e verificar o pom.xml.
  • Procurar pela tag <repositories>.

Exemplo:

<repositories>
    <repository>
        <id>mobilepf</id>
        <url>https://nexusrepository.bradesco.com.br:8443/repository/mobilepf-maven-central</url>
    </repository>
</repositories>
  • Validar se a URL pertence a um repositório acessível pela aplicação.
  • Caso não pertença à VS_KEY do projeto, remover essa configuração.
  • Verificar outros repositórios indevidos (ex: http://repo1.maven.org/maven2).
  • Realizar novo build.

1.9 Falha no build - dist/package.json não encontrado

Olá! 👋

Identificamos um problema na etapa de criação do package.json no diretório dist, pois a pasta não está sendo gerada durante o build.

🔍 O que isso significa?
Significa que o build irá falhar, pois a pasta dist não será encontrada.

✅ O que você deve fazer:

  • Verificar o arquivo package.json.
  • Validar se o projeto realmente necessita da instrução de build.

Caso NÃO necessite:

  • Remover a instrução que depende da pasta dist.

Caso necessite:

  • Criar a pasta dist durante o build.

Exemplo:

  • Realizar novo build.

1.10 OCP Migração Híbrida - Erro na etapa Build artefato (No tests were executed)

🧠 Resposta da BIA TECH – Falha na execução de testes unitários pelo Maven

Olá! 👋

Identificamos que a etapa de Build artefato falhou porque o plugin maven-surefire não conseguiu executar os testes unitários.

🔍 O que isso significa?
O build irá falhar porque os testes unitários não estão sendo executados corretamente.

Esse problema pode ocorrer porque não há configuração do plugin dentro do <pluginManagement> no pom.xml.

✅ O que você deve fazer:

  • Acessar o pom.xml.
  • Buscar a tag <pluginManagement>.
  • Adicionar o plugin:
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-surefire-plugin</artifactId>
  <version>3.0.0-M3</version>
</plugin>
  • Caso necessário, utilizar a versão: 3.0.0-M7
  • Executar novo build.

🎯 Motivo:
Erro Build

👥 Time responsável:
DevOps

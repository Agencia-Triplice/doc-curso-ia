1.1 Erro de Falha de sincronização com o ArgoCD - Erro de pull na imagem no repositorio - Aplicação em estado Degraded. Verifique os eventos dos pods pelo ArgoCD - Error: ImagePullBackOff - Failed to pull image - is waiting to start: trying and failing to pull image 

🧠 Resposta da BIA TECH – A etapa Sincronizando aplicação com o ArgoCD falhou por conta da aplicação estar degraded.

Olá! 👋
Identificamos que a aplicação encontra-se degraded. Isso pode significar que o<artifactId>, ou então o <finalName>, ambos no pom.xml estão apontando para um nome incorreto. O artifactId é o campo responsável que contém o nome do artefato gerado na etapa de build, normalmente um .jar, ou .war dependendo do que está declarado no <packaging>. Se por exemplo o repositório for o dvop-srv-pipeline, então deve estar sendo usado dentro da <artifactId> conforme exemplo:

     <groupId>br.com.bradesco.bcpf</groupId>
     <artifactId>dvop-srv-pipeline</artifactId>

Note que o dvop-srv-pipeline dentro do <artifactId> é o mesmo do nome do repositório. E também é interessante validar o que está declarado no <finalName>. O campo finalName também devem apontar para

artifactId, ou então conter diretamente o nome do repositório. O finalName será o nome final do artefato gerado. Segue um exemplo:

<build>
        <finalName>${project.artifactId}</finalName>

....

Ou então

<build>
        <finalName>dvop-srv-pipeline</finalName>

....

🎯 Motivo:

Erro Deploy

🔍 O que isso significa?

Significa que o seu deploy irá falhar por conta de não conseguir realizar o pull da imagem Docker no Nexus.

✅ O que você deve fazer:

  1. Acessar o pom.xml da aplicação.
  2. Localizar a tag <artifactId>
  3. Apontar para o nome do seu repositório.
  4. Verifique se foi declarado o <finalName> dentro de <build> no pom.xml. Caso não esteja, deve ser criado. Caso já esteja verifique se o <finalName> aponta para o artifactId ou então aplicar diretamente o nome do repositório.
  5. Realizar novo build.

1.2 Erro de Falha de sincronização com o ArgoCD - Aplicação em estado Degraded. Verifique os eventos dos pods pelo ArgoCD  - Startup probe failed: connect: connection refused

🧠 Resposta da BIA TECH – A etapa Sincronizando aplicação com o ArgoCD falhou por conta de uma divergência entre a porta do Tomcat e a porta Service no values.yaml

Olá! 👋
Identificamos uma falha de sincronização com o ArgoCD durante a etapa de deploy, causando o erro de Startup probe failed. Esse erro ocorre porque não foi possivel realizar uma requisição para o /health/liveness que está configurado dentro da propriedade de probes → startupProbe no values.yaml do seu repositório de configuração. Esse erro pode indicar que a porta configurada do servidor Tomcat está divergente da porta configurada do service no values.yaml do repositório de configuração.


🔍 O que isso significa?

Isso significa que a aplicação estará sendo inicializada em uma porta e o service da aplicação estará disponível em outra porta. Quem disponibiliza os endpoints de /health é próprio spring-boot-starter-actuator, então com essa divergência entre as portas p deploy irá falhar por conta que não consegue realizar a requisição para o /health/liveness, causando o estado degraded no Pod.

✅ O que você deve fazer:

  1. Verificar o values.yaml na branch correspondente ao ambiente no repositório de configuração. Lembrando que sandbox representa o ambiente de desenvolvimento, staging representa o de homologação e production representa o de produção.
  2. Realizar uma busca da propriedade service e dentro dela a port. Segue um exemplo de como o service está configurado no values.yaml:service:
        # Defina a porta da sua aplicação.
        port: 8080
  3. Realizar uma busca da varíavel SERVER_PORT no configmap e comparar com a port do service. Segue um exemplo:configmap:
        SERVER_PORT: 8087
  4. Equalizar as portas. No caso, a port do service deve estar configurada na 8087, conforme o exemplo.
  5. Realizar novamente o deploy de infraestrutura.

ℹ️ Informações:

Branches x ambiente do repositório de configuração

DEV - sandbox

HOM - staging

PRD - production

🧠 Resposta da BIA TECH – Detectamos uma falha na etapa de Falha de sincronização com o ArgoCD que pode estar relacionada aos parâmetros inválidos da JVM/JAVA_OPTS.

Olá! 👋

Ao acessar os logs do pod no ArgoCD foi identificado que os parâmetros que estão declarados dentro da variável de ambiente JAVA_OPTS podem estar inválidos. 

🔍 O que isso significa?

Significa que o deploy irá falhar por conta não conseguir validar corretamente os parâmetros da JAVA_OPTS.

✅ O que você deve fazer:

  1. Acessar os logs do pod no ArgoCD e verificar se ocorreu erro de JAVA_OPTS.
  2. Caso sim, acessar o values.yaml do repositório de configuração na branch do ambiente relacionada.
  3. Procurar por configmap e a varíavel JAVA_OPTS que está dentro dele.
  4. Verifique se o valor do Xms está maior que o valor Xmx. Ex: Xms 769 Xmx 768. Caso esteja, está incorreto.
  5. Corrija para que o valor do Xmx esteja maior que o valor do Xms. Exemplo: Xms 768 Xmx 769.
  6. Efetue um novo deploy.

1.5 Erro de Falha de sincronização com o ArgoCD - Sync Failed no ArgoCD - Mensagem da operação: one or more objects failed to apply, reason: error when patching "/dev/shm/1134703300":  "" is invalid: patch: Invalid value: "": unrecognized type: string OU Mensagem de Operação: Invalid value: "": cannot convert int64 to string

🧠 Resposta da BIA TECH – Detectamos uma falha na etapa Sincronizando Aplicação no ArgoCD

Olá! 👋

A sincronização da aplicação com o ArgoCD falhou e retornará Sync Failed no LAST SYNC no ArgoCD. Ao clicar no Sync Failed pode aparecer a seguinte mensagem: is invalid: patch: Invalid value: "": unrecognized type: string.

Isso acontece porque pode conter varíaveis booleanas e/ou numéricas dentro do configmap no values.yaml que não estão como String(entre aspas). Esses tipos de variáveis devem obrigatoriamente serem colocadas entre aspas.

Essa mensagem de operação também pode ocorrer: is invalid: patch: Invalid value: "": cannot convert int64 to string. Nesse caso é ideal validar também se há variáveis numéricas do configmap que estão sem aspas e/ou com aspas simples. No caso devem estar obrigatoriamente com aspas duplas.

Exemplo:

SERVER_PARALELISM: "200" → Valor numérico entre aspas

LOG_ON: "true" → Valor booleano entre aspas

🔍 O que isso significa?

Significa que o deploy irá falhar porque o helm não conseguirá realizar o parser das variáveis corretamente, causando falha na sincronização da aplicação com o ArgoCD.

✅ O que você deve fazer:

  1. Acessar o values.yaml no repositório de configuração.
  2. Verificar o configmap e identificar os valores das variáveis que são númericas e/ou booleanas.
  3. Caso estejam sem aspas, coloca-las entre aspas. Caso esteja com aspas simples, aplique aspas duplas.
  4. Efetuar novamente o deploy de infraestrutura.

1.16 Erro Log destination localhost/<unresolved>:5170: Waiting 4999ms before attempting reconnection

🧠 Resposta da BIA TECH – Detectamos um WARN gerado na inicialização do Pod.

Olá! 👋

Foi detectado nos logs um WARN informando que houve uma tentativa de conexão local com localhost:5170 por meio da dependência enge-lib-logcloud-spring-starter que é responsável pela geração e publicação de logs.

Esse WARN é gerado quando são realizadas as configurações dessa biblioteca somente no application.yaml e também quando há essa tentativa de realizar deploy no ambiente de desenvolvimento, homologação ou produção.

Somente com as configurações aplicadas no application.yaml localmente irá funcionar e haverá a conexão, por isso é feita essa conexão local na porta 5170. Porém para funcionar no ambiente corretamente é necessário configurar em conjunto com o fluentbit e os tópicos Kafka para correta publicação dos logs da aplicação.

🔍 O que isso significa?

O seu deploy possívelmente não irá falhar, mas esse WARN permancerá durante a inicialização.

✅ O que você deve fazer:

  1. Verificar se a sua aplicação utiliza o fluentbit e deve publicar os logs no tópico Kafka.
  2. Caso utilizar, acessar a documentação: [IngLog] - Log de Aplicações Leap - Java - FluentBIT e configurar em conjunto com o fluetbit e demais adaptações.
  3. Caso não utilizar será necessário verificar as configurações dessa dependência dentro do projeto para que não sejam utilizadas no ambiente, somente local.

1.41 Falha no deploy “failed to mount objects, error: failed to get objectType:secret, objectName:mspb-ibmmq-cert, objectVersion:: keyvault.BaseClient#GetSecret: Failure responding to request: StatusCode=403 -- Original Error: autorest/azure: Service returned an error. Status=403 Code="Forbidden"” após habilitar keyvault.

🧠 Resposta da BIA TECH:
Ocorreu uma falha no deploy por não encontrar o KeyVault ou não ter as devidas permissções de GET/List do Service Principal do Keyvault. 

🎯 Motivo:
O Keyvault não foi criado pelo time de engenharia cloud ou não tem as devidas permissões vinculadas ao SPN que também deve ser feito pelo de eng.Cloud.

🔍 O que isso significa?

O Deploy só irá funcionar após a criação do KeyVault e a configuração no namespace.

✅ O que você deve fazer

O Analista deve entrar em contato com o time de Engenharia Cloud e pedir para criar o KeyVault no devido ambiente ou ajustar as devidas permissões, também será necessário acionar o time de segurança para o cadastro de secrets no KV;

👥 Time responsável:
Engenharia Cloud.
